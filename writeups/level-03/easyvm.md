## Постановка задачи

Программа запрашивает десятисимвольный лицензионный ключ. Проверка выполняется не прямыми сравнениями, а небольшой виртуальной машиной, которая интерпретирует последовательность трехбайтовых инструкций.

От строки приглашения

```text
Please Enter 10-char License Key:
```

через cross-reference находим подготовку bytecode и вызов интерпретатора `sub_140001EC0`.

## Набор инструкций

Анализ диспетчера внутри `sub_140001EC0` позволяет сопоставить opcode и семантику:

| Opcode | ASCII | Семантика |
| --- | --- | --- |
| `0x49` | `I` | Загрузить непосредственное значение в аккумулятор |
| `0x4F` | `O` | Сохранить аккумулятор в один из 16 регистров |
| `0x41` | `A` | Прибавить операнд к аккумулятору |
| `0x53` | `S` | Вычесть операнд из аккумулятора |
| `0x58` | `X` | Выполнить XOR аккумулятора с операндом |

Примеры обработчиков:

```asm
; I — load immediate
movzx   eax, byte ptr [r11+rdi+1]

; O — store accumulator
movsx   rcx, byte ptr [r11+rdi+1]
and     ecx, 0Fh
mov     byte ptr [rsp+rcx+18h+var_18], al

; S — subtract
sub     al, [r11+rdi+1]

; X — xor
movzx   edx, byte ptr [r11+rdi+1]
xor     al, dl
```

Третий байт инструкции определяет режим операнда. Значение `0x41` выбирает альтернативный путь чтения, поэтому при ручном разборе нужно рассматривать все три байта, а не только opcode и непосредственное значение.

## Условие успеха

После интерпретатора выполняется проверка возвращенного аккумулятора:

```asm
call    sub_140001EC0
lea     ebx, [rax+2]
test    al, al
setz    cl
mov     eax, r12d
cmp     bl, 2
setz    al
test    eax, ecx
jnz     short success
```

Успешный путь требует, чтобы итоговое значение аккумулятора было равно нулю.

## Динамическая проверка bytecode

Breakpoint на вызове VM (`EasyVM+0x23D2` в исследованной сборке) позволяет посмотреть буфер через `RDX`. Ввод `0123456789` удобен тем, что визуально связывает байты bytecode с позициями ключа.

Наблюдаемый фрагмент:

```text
49 5A 30 4F 01 41 49 5A 30 4F 02 41 49 01 41 41
5A 30 53 4B 30 53 02 41 41 0A 41 4F 0A 41 30 00
```

Первые инструкции сохраняют два символа во временные регистры. Далее последовательность вычитаний и сложений формирует ограничения для позиций ключа. Пять явных вычитаний кодируют префикс:

```text
KEY-K
```

Для следующих двух значимых позиций VM сохраняет символы в разные регистры, вычитает один и прибавляет другой. Чтобы аккумулятор остался нулевым, эти символы должны совпадать.

Итоговая форма принятого ввода:

```text
KEY-Kxx...
```

где обе позиции `x` содержат один и тот же ASCII-символ. В исследованной сборке проверка длины позволяет добавлять хвост после значимых позиций.

Подтвержденный пример:

```text
Please Enter 10-char License Key: KEY-KzzMEOWMEOWMEOW
CORRECT!!!!!
```

## Вариант с patching

Вместо изменения условного перехода можно принудительно подготовить значение, которое ожидает последующее `cmp bl, 2`: заменить вычисление

```asm
lea ebx, [rax+2]
```

на эквивалентную по размеру последовательность, устанавливающую `BL` в `2`. Это обходит проверку результата VM, но не объясняет формат корректного ключа, поэтому основным решением остается восстановление bytecode.
